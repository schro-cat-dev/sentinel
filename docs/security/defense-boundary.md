## 2. 各境界の設計根拠とコストトレードオフ

### B1: SDK入口 (LogValidator / ingest)

| 項目 | 詳細 |
|------|------|
| **配置理由** | ユーザーアプリケーションから受けるデータはすべて非信頼。最初の接触点で検証する「Fail Fast」原則 |
| **実装コスト** | 低。TypeScript型システム + バリデーション関数。ランタイム依存追加なし |
| **防御内容** | 型検証、必須フィールド、最大長(64KB)、null byte検出、フォーマット検証 |
| **トレードオフ** | 検証のCPUオーバーヘッドは1ログあたり < 0.1ms。高スループット環境でも無視できるレベル |
| **なぜここか** | 内部パイプラインを信頼ゾーンとして扱うことで、以降のコンポーネントがバリデーションコストを二重払いしない。入口一箇所で防御することで、内部の各コンポーネントはビジネスロジックに集中できる |
| **代替案と棄却理由** | 各コンポーネントで個別検証 → コード重複・整合性の維持コスト大。信頼境界を2つに分けるメリットがない |

### B2: SDK出口 (Transport / User Handlers)

| 項目 | 詳細 |
|------|------|
| **配置理由** | SDKはクライアントライブラリであり、Transport先（gRPCサーバ、Webhook等）の接続設定はSDK利用者の責務 |
| **なぜSDK内で防御しないか** | TLS証明書、認証トークン、エンドポイントURLは利用者の環境固有。SDKが全パターンを防御するのは不可能であり、責務の越境になる |
| **トレードオフ** | SDKがinsecure接続を許容することで、開発・テスト環境の利便性を維持。ただし**本番環境でのinsecure使用リスク**をドキュメントで明示する義務がある |
| **改善案** | `Transport` インターフェースに `isSecure(): boolean` メソッドを追加し、production環境では警告を出す仕組み |

### B3: ネットワーク境界 (Go Server入口)

| 項目 | 詳細 |
|------|------|
| **配置理由** | ネットワーク越しの通信は完全非信頼。認証・認可・レートリミット・完全性検証をサーバ入口で行う |
| **実装コスト** | 中。TLS設定、API Key認証、HMAC検証、レートリミッター。gRPC interceptorとして実装 |
| **防御内容** | TLS暗号化（通信機密性）、API Key認証（アクセス制御）、レートリミット（DoS防御）、HMAC検証（改竄検知） |
| **トレードオフ** | TLS + HMAC検証のレイテンシ追加は1リクエストあたり約0.5-2ms。セキュリティ対レイテンシのトレードオフとして十分に正当化される |
| **なぜここか** | ゼロトラスト原則。クライアントSDKで検証済みでも、ネットワーク上での改竄可能性を排除できないため、サーバ側で再検証する。B1（クライアント検証）は「善意の利用者のバグ防止」、B3は「悪意ある攻撃の防御」という異なる目的を持つ |

### B4: ストレージ境界 (SQLCipher)

| 項目 | 詳細 |
|------|------|
| **配置理由** | 永続化データに対するat-rest暗号化。ディスクアクセスやバックアップ流出時の機密性保護 |
| **実装コスト** | 低〜中。SQLCipherはSQLite互換でドライバ差し替えのみ。鍵管理が主要コスト |
| **防御内容** | AES-256暗号化、鍵ローテーション対応 |
| **トレードオフ** | 書き込み性能が約5-15%低下（SQLCipher公式ベンチマーク）。ログシステムの特性上、読み取り頻度は書き込みより低いため許容範囲 |
| **なぜここか** | データの最終保管場所であり、他の全境界を突破されても最後の防御線として機能する。Defense in Depthの最内層 |

## 3. 防御しない領域とその根拠

### SDK内で防御しない領域

| 領域 | 根拠 |
|------|------|
| **OS/ランタイムの脆弱性** | Node.jsランタイムやOSカーネルの脆弱性はSDKの責務外。利用者のパッチ管理に委ねる |
| **利用者ハンドラの安全性** | `TaskExecutor` に登録されるユーザー定義ハンドラの内部実装はSDKが制御できない |
| **ネットワーク構成** | ファイアウォール、VPN、mTLS等のネットワークレベルの保護はインフラ層の責務 |
| **鍵管理** | HMAC鍵、API鍵の生成・保管・ローテーションは利用者のSecret Management責務 |
| **監査ログの保全** | ログの長期保管・改竄防止ストレージ（WORM等）はインフラ層の責務 |

### コスト見合いで採用しなかった防御策

| 防御策 | コスト | 効果 | 判断 |
|--------|-------|------|------|
| WAF統合 | 高（外部サービス依存） | SDKレベルでは無意味 | **不採用** — サーバ/インフラ層で実装すべき |
| コードサイニング | 中（CI/CD統合必要） | サプライチェーン保護 | **将来検討** — npm provenance対応を優先 |
| Canaryトークン | 低 | 内部漏洩の早期検知 | **将来検討** — v1.0以降 |
| サンドボックス実行 | 高（VM/isolate必要） | ハンドラの隔離 | **不採用** — パフォーマンス劣化が大きすぎる |
| 正規表現タイムアウト | 中（Worker thread必要） | ReDoS完全防御 | **検討中** — C-001修正で十分な場合は不採用 |

## 4. Defense in Depth マップ

```
脅威                        B1        内部      B2        B3         B4
────────────────────────────────────────────────────────────────────────
不正入力 (injection)        ✅ 検証    ─         ─         ✅ 再検証   ─
ReDoS                       ✅ 長さ制限 ⚠ 要修正  ─         ─          ─
情報漏洩                    ─         ✅ マスク   ─         ─          ✅ 暗号化
改竄                        ─         ✅ HMAC    ─         ✅ HMAC検証 ✅ 暗号化
盗聴                        ─         ─         ─         ✅ TLS      ✅ 暗号化
DoS                         ✅ 長さ制限 ─         ─         ✅ Rate     ─
認証バイパス                ─         ─         ─         ✅ API Key  ─
サプライチェーン攻撃         ✅ 依存0   ─         ─         ─          ─
────────────────────────────────────────────────────────────────────────
✅ = 防御済み  ⚠ = 要改善  ─ = 該当なし/他層が担当
```

## 5. 責務分離: クライアント vs サーバ

| 責務 | クライアントSDK (TS) | サーバ (Go) |
|------|---------------------|-------------|
| 入力バリデーション | ✅ 形式・長さ・型 | ✅ 再検証（信頼しない） |
| PIIマスキング | ✅ 送信前にマスク | ❌ マスク済み前提 |
| ハッシュチェーン生成 | ✅ SHA-256署名 | ❌ 検証のみ |
| ハッシュチェーン検証 | ❌ | ✅ HMAC検証 |
| TLS終端 | ❌ Transport層に委譲 | ✅ gRPC TLS |
| 認証 | ❌ トークン付与のみ | ✅ API Key検証 |
| レートリミット | ❌ | ✅ サーバ側で制御 |
| データ暗号化 (at-rest) | ❌ | ✅ SQLCipher |
| 鍵管理 | ❌ 利用者責務 | ✅ 環境変数/Vault |
